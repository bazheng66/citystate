# 对比实验报告：Tauri 做图形应用的边界在哪

测试日期 2026-11-13。机器：i9-14900HX，RTX 4060 Laptop，32GB，2560×1600 @ 240Hz（系统缩放 150%），Windows 11。

被测对象是「城邦演武」v3：一个纯 Canvas 2D 的即时战略游戏，逐士兵模拟，地图最大 200×125 格、8 方、上万士兵。同一份页面分别放进 Tauri 2（WebView2）、Electron 45 和 Edge 里跑同一套压力测试，另外拿改造前的版本做前后对比。测试方法和原始数据见文末与 `bench/results/`。

## 结论

**1. 在这个规模上，Tauri 的图形性能没有成为瓶颈，和同内核的 Edge 持平。**
大地图 6 方混战，Tauri 在 1000 / 3000 / 6000 / 10000 兵时平均 238 / 202 / 138 / 86 FPS；Edge 是 237 / 201 / 139 / 87。两者用的是同一个 Chromium 157，差距在测量误差内。也就是说 WebView2 这层壳本身没有带来可测的图形开销，瓶颈在页面自己的 JS 和 Canvas 2D。

**2. Electron 在重负载下慢 12–17%。**
同样四档是 233 / 178 / 118 / 72 FPS。差距主要出在全图俯瞰阶段（6000 兵时 80 对 124 FPS），近景几乎没差别。Electron 45 自带的是 Chromium 156，比系统 WebView2 旧一个大版本；这个差距是内核版本造成的还是 Electron 的默认配置造成的，本实验分不出来。

**3. 边界在哪：约 1 万兵时仍可玩，再往上先撞到的是 JS 侧的绘制指令，不是外壳。**
10000 兵时 Tauri 平均 86 FPS，最差 1% 的帧约 39 FPS，30 秒里有 13 帧超过 33ms，没有超过 100ms 的。此时每帧模拟 1.7ms、JS 侧发绘制指令 7.3ms。巨型地图（200×125 格、99 座据点、8 方、10000 兵）因为兵更分散，反而有 131 FPS。本实验没有测 1 万兵以上，所以“多少兵会掉到 30 FPS 以下”没有数据。

**4. 稳定性：Tauri 8 分钟浸泡没有一帧超过 33ms，没有脚本错误；内存在缓存填满后持平。**
4000 兵、8 分钟、近 8 万帧，最长一帧 25ms。进程树私有内存前半段从约 570MB 涨到约 740MB，后半段持平（737 → 755 → 746MB）；另一轮 5 分钟近景浸泡同样在约 650MB 处持平。Electron 和 Edge 的走势相同。需要说明的局限：两轮浸泡里地形缓存都没有涨到 44MP 的上限，所以“缓存淘汰”这条路径没有被实际触发过；8 分钟也不足以排除很慢的泄漏。

**5. 体积和内存：Tauri 的可执行文件 3.5MB，Electron 打包目录 357MB；运行时内存两者接近。**
停在标题页时进程树私有内存 Tauri 432MB、Electron 402MB、Edge 654MB。Tauri 的体积优势来自复用系统里的 WebView2，内存上没有优势。启动到可交互 Tauri 约 1.1–1.4 秒，Electron 约 0.85 秒。

**6. 改造本身：同屏约 2000 兵，新版比旧版快约 70%，同时多了光照、粒子、迷雾等特性。**
Tauri 里旧版 40 FPS，新版 69 FPS；Edge 是 42 对 70。有意思的是新版 JS 侧耗时反而略高（11.2ms 对 9.8ms），帧率却更高 —— 省下来的是 GPU 侧：所有精灵帧合进了一张图集，影子和脚环从逐个画路径改成了贴图。Electron 那一行旧版只投放到约 1600 兵，负载偏轻，不能直接比。

**7. 钱花在哪：旗标和血条最贵，LOD 最值，光照几乎免费。**
6000 兵时关掉旗标血条 137 → 178 FPS（俯瞰阶段 123 → 224）；关掉 LOD 则俯瞰阶段从 123 掉到 29 FPS；关掉昼夜光照没有可测的变化。旗标是用路径和文字逐个画的，下一步该把它也缓存成贴图。

## 一个没查明的现象

实验过程中有若干轮出现“窗口整体降到约 1 帧/秒、CPU 占用很低”，结果作废后重跑。按外壳统计（不含启动测试）：**Tauri 17 轮 0 次，Electron 15 轮 4 次，Edge 17 轮 6 次**。

已经排除的原因：窗口被遮挡（专门做了遮挡测试，三个外壳被盖住后都照常出帧，见数据表第七节）、页面代码里的可见性或定时器逻辑（没有）。没有排除的：桌面状态变化（熄屏、锁屏、全屏应用）、Windows 对后台进程的调度策略。异常在时间上成段出现，加了诊断代码后又不复现，所以原因没有定位。

这个统计对 Tauri 有利，但样本小、原因不明，**不能据此下“Tauri 更稳定”的结论**，只能说本次实验里 Tauri 没有出现过。实验脚本现在会把 CPU 占用异常低的轮次判为无效并自动重跑。

## 这次实验没有回答的问题

- 只测了一台机器、一块独显、Windows。集成显卡、macOS（WKWebView）和 Linux（WebKitGTK）上 Tauri 用的是完全不同的内核，结论不能外推。
- 只测了 Canvas 2D。WebGL / WebGPU 下各外壳的差距可能不一样，也是突破当前 JS 侧瓶颈最直接的方向。
- “JS 侧渲染耗时”不含 GPU 光栅化，后者只能从帧率间接看出来。
- 每个配置只跑了一轮（启动测试三轮），没有给出方差。相邻档位之间几个百分点的差别不应该当真。
- 浸泡最长 8 分钟。

## 方法

- 压力测试里所有归属方都由 AI 托管，据点打不坏，兵死了按模拟步数补充，所以各外壳里的战局逐步一致，负载稳定。
- 相机脚本：近景沿 8 字巡游（持续烘焙新地形块）→ 拉远 → 全图俯瞰（所有兵都在屏幕里）→ 中景。
- 每轮新开进程，页面把结果 POST 回本地服务；脚本每 2 秒采样一次整棵进程树的工作集、私有内存和 CPU 时间。
- Tauri 加载的是嵌进可执行文件的页面，Electron 读本地文件，Edge 走本地 HTTP；改造前的页面三个外壳都走本地 HTTP。
- 三个外壳的窗口内容区都是 1360×900，画布 2040×1128。
- 复现：`npx tauri build --no-bundle`、`npm --prefix electron run pack`、`node tools/experiment.js all`、`node tools/report.js`。
